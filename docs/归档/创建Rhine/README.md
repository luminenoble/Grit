## 已确定的规则

这些规则直接实施，阶段评审主要检查实现效果，通常无需重新询问业务定义：

- Android 手机；Rhine 页面锁定横屏、全屏沉浸，不显示底部导航，画面与 HUD 版式以[参考图](../../Rhine_reference.png)为准，规格见总方案 8.6。不做竖屏适配，不新增桌面或 Web 的独立 Rhine 设计目标。
- 米色块体占满场景，列方向从右下到左上（块长边向右上约 29°，同参考图）；全部块的顶面和侧面都显示贴面文字；颜色只改变文字。
- 第一层：列为 Category，块为 Task；第二层：列为同类别的 Task，块为 Section。
- 两层 0 号块分别操作 Category / Task；真实内容序号从 1 开始，稳定 ID 不随排序改变。
- 0 号块可以离屏，通过“回到开头”返回。所有列共享沿列偏移。
- 静止时只有中心列起伏，中心列最低块仍高于非中心列。高度只表达焦点。
- 预览、详情、调整三个模式；非中心列首次点击只定位；详情/调整操作从中心列开始。
- 只尾部追加一个真实对象，保存后移动视角；占位不落库，不生成中间空数据。
- 逻辑边界限制浏览范围，视口边缘的装饰块没有业务操作；避免无限空区和无限渲染。
- Task 手动完成独立于 Section 日期；Rhine 包含已完成 Task，不采用列表的隐藏已完成筛选，也不把“今天”复制成真实类别。
- 业务数据和新格式备份沿用现有架构，旧 JSON 转换仍由用户提供文件后在应用外处理。

## agent 的共同执行要求

1. 读取仓库 AGENTS.md、本总览、当前阶段文档、[进度与确认记录](进度与确认记录.md)，再阅读前阶段交付记录和截图。检查工作区现有改动，保持其他 agent 和用户的工作。
2. 本轮完成用户指定的阶段。阶段文档的后续功能作为交接信息，跨阶段增加工作需有用户授权。
3. 接入现有模型、TaskRepo 和编辑组件。新增仓库能力时维护事务、稳定 ID、连续 orderIndex 与新 JSON 格式约定。
4. 按可视窗口读取摘要，不使用全量正文流作为 Rhine 概览来源；所有位移使用同一份投影及边界计算。
5. 技术验证和视觉确认分别记录。编译通过不能替代实际交互或视觉验收。
6. 阶段完成前交付代码、测试结果、可运行包、截图/必要录屏、实现记录及待确认问题，再让用户评审。不能仅交计划或一张设计效果图。
7. 用户要求调整时，完成调整和针对性复验，提供新版截图并记录替代关系。下一位 agent 采用最后确认的版本。
8. 最终回复链接到工作文档和图片，概括完成范围、验证结果、限制，并提出本阶段 2–3 个具体确认问题。既有业务规则保持不变，视觉修改先记录其是否影响后续接口。

## 现有代码基础

| 内容 | 路径 / 接口 |
| --- | --- |
| 模型与仓库接口 | `shared/core/src/commonMain/kotlin/com/shub39/grit/core/tasks/` |
| 独立数据表、事务实现 | `androidApp/src/main/java/com/shub39/grit/tasks/data/` |
| 新备份格式 | `shared/core/src/commonMain/kotlin/com/shub39/grit/core/settings/backup/RhineBackup.kt` |
| 类别与任务编辑 | `shared/ui/src/commonMain/kotlin/com/shub39/grit/shared/ui/task/ui/component/` |
| 导航占位 | `shared/ui/src/commonMain/kotlin/com/shub39/grit/shared/ui/app/MainApp.kt`、`AppSections.kt` |
| 米色基础主题与文字颜色 | `shared/ui/src/commonMain/kotlin/com/shub39/grit/shared/ui/theme/` |
| 设置接口与 Android 实现 | `SettingsDatastore.kt`、`SettingsDatastoreImpl.kt`，以及 Setting 的 Action/State/ViewModel |

优先复用 `getCategoriesFlow`、`getTaskSummariesFlow`、`getSectionSummariesFlow`、`getCategoryCountsFlow`、`getTaskCountsFlow`、`searchTasks`，以及各类 upsert / delete / move 接口。`moveTask/moveCategory/moveSection` 接受从 0 开始的目标位置；界面输入的序号需减 1。现有摘要查询 limit 为 1–500，offset 必须非负。

Rhine 文件建议集中于 `shared/ui/src/commonMain/kotlin/com/shub39/grit/shared/ui/rhine/`；Android 专用能力放平台 source set。投影、边界、视口、命中和排序计算独立于表单与绘制，避免一个屏幕函数承载全部业务。

## 截图与确认协议

### 每期都提交可查看的证据

- 图片来自本阶段实际运行的代码，优先 Android 实机/模拟器截图；原始 PNG 保存到对应交付目录。
- 每张截图说明设备或运行环境、Android 版本、屏幕尺寸/密度、数据样例、模式、层级、焦点和相关参数。
- 可另附标注图用于说明，原始截图一并保留。辅助设计稿明确标为设计稿。
- 交付前 agent 自己查看截图，修复文字裁切、空白、遮挡错误、控件越界等明显问题，再交给用户看。
- 动态阶段提交短录屏，截图用于审阅布局与状态，录屏用于审阅起伏、切换、拖动和补位速度。
- 测试样例使用隔离的测试库、测试构建或开发预览，不覆盖用户数据。截图中的样例不能伪称为用户实际记录。

阶段 01、03、06 是重点视觉确认点；其他阶段同样提交截图，阶段 02、03、05、07 还需动态证据。

### 获取截图的环境暂不可用时

之前存在 ADB 探测超时，不能假设设备已经可用。阶段开始时检查构建与截图条件，尝试恢复可用的本地预览环境。

若仍无 Android 截图条件，交付已完成代码、APK、复现步骤和明确的环境问题。可以附运行共享代码得到的桌面预览，但标明“代码预览，非 Android 手机截图”。记录状态为“代码完成，待手机截图/用户确认”，不把缺失图片的视觉验收记为通过。

此时不伪造手机截图，也不通过改写业务要求来回避确认。当前阶段独立的测试、构建和交接仍须完成。用户可以授权下一步或指定设备验收方式。

### 确认如何记录

阶段最终问题围绕“这次截图/录屏是否需要调整”，附具体图片名和关注点。提供“按当前效果继续 / 按指出的问题调整”这样的简短选项即可。

用户未回复、工具没有返回答案、默认预选项均不代表确认。将明确的用户回复、确认的构建/截图版本和待调整事项写入[进度与确认记录](进度与确认记录.md)。下一阶段已被明确授权时记录该授权，不伪造此前视觉确认。

## 构建与验证

本项目要求 Java 21。当前工作记录给出的临时工具链目录为 `/tmp/grit-jdk-root/usr/lib/jvm/java-21-openjdk-amd64`，使用前检查是否仍存在，也可使用其他有效 Java 21 环境。

通常的构建入口：

```sh
./gradlew :androidApp:copyRhineDebugApk
```

按改动运行相关单元测试、Android 测试代码编译、格式检查。共同代码或接口变化时验证 JVM/Wasm source set；阶段 07 执行完整回归。数据库设备测试之前仅编译通过，已有 7 项模型测试通过；阶段执行者以当前代码重新验证受影响部分，不沿用旧记录充当新结果。
